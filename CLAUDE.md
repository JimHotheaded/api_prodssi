# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A read-only Express REST API that exposes SCADA historian data from a SQL Server (`192.168.100.100`, config in `config.js`) for a manufacturing plant. Data originates from Kepware/FactoryTalk tag logging into per-machine `REPL_*` databases — at ~15s cadence since 2026-08-06, ~10s before that (see the `CADENCE_ERAS` gotcha below; both cadences live in the history permanently).

**This repo went live on 2026-07-09** as the production API on port 3334 (overridable via `PORT`), serving Node-RED dashboards and other consumers at `http://172.30.1.112:3334`. It replaced the previous production copy after a full endpoint differential (`test/live/test-full-endpoint-diff.js`) showed byte-identical behavior except the deliberate improvements (gap-filled `count*` defaults, BM2_con `/avg` fix, threshold 400). To test risky changes side by side again, run a second copy with `PORT=3336 node server.js`.

## Running

```
node server.js
```

`npm test` runs the offline unit suite (`test/fillgaps-unit.js` + `test/alarm-params-unit.js` — no network/DB needed). `test/live/` holds differential tests that byte-compare a candidate copy on :3336 against the running production server on :3334 on fixed historical windows; they need the plant network and both servers up (see `test/live/README.md`). They were written for the 2026-07-09 go-live (old production on :3334); to reuse them for a future change, run the new candidate on :3336 and re-check the whitelisted expected diffs. No lint, no build step. Fresh clone: `npm install`, then copy `config.example.js` to `config.js` and fill in credentials (or set `DB_USER`/`DB_PASSWORD`/`DB_SERVER` env vars).

## Architecture

- `server.js` → `app.js` → mounts `api/routes/plants.js` at `/plants` and the self-contained alarm module `api/alarms/` at `/api/alm`.
- `config.js` (gitignored; template in `config.example.js`) exports `{dbConfig_PROD}` — a single shared `mssql` pool config (pool created once at the top of `plants.js`). Credentials come from `DB_USER`/`DB_PASSWORD`/`DB_SERVER` env vars with hardcoded fallbacks.
- `utils.js` — shared aggregation helpers (`findMax`, `findMin`, `calculateAverage`, `countValues`, `countValuesHour`, `calCap`, `isHoliday`/`isHolidayUTC`, `fillGaps` and friends) plus a hardcoded Thai holiday list (2025–2027) that needs annual updating (2027 carries a TODO to re-verify against the Cabinet announcement).
- `api/tagDisplay.js` — presentation layer applied on the way out: friendly tag names and engineering-unit scaling, keyed by plant (`RRM` and `OFIL` today). See the display-layer gotcha below.

### plants.js route pattern (the big picture)

`plants.js` (~2000 lines) is one repeated block per machine/plant, copy-pasted ~17 times. Each plant (e.g. `BM2`, `BM2_con`, `CT6_con`, `CT6_heater`, `CT7_con`, `CT7_heater`, `CSH`, `FeedRaw`, `HYD`, `RMM1`, `RMM2`, `RRM`, `LC_CSH`, `Hour_OFIL`, `OFIL`, `Silo`, `WL`) maps to its own database + tag/float table pair (e.g. `[REPL_BallMill_Log].[dbo].[TagBallMill]` / `[FloatBallMill]`) and gets the same 6 routes:

- `GET /plants/{plant}` — list tags (TagName/TagIndex)
- `GET /plants/{plant}/all` — top 1000 raw rows
- `GET /plants/{plant}/:tagIndex` — latest value for a tag
- `GET /plants/{plant}/:tagIndex/:tbf/:taf` — raw rows in a time window (`tbf`/`taf` = time before/after, format `2024-07-01 00:00:00.000`, URL-encoded)
- `GET /plants/{plant}/:tagIndex/:tbf/:taf/avg` — min/max/avg aggregated in SQL (since 2026-07-20; was fetch-all-rows + JS)
- `GET /plants/count{plant}?tagIndex=&tbf=&taf=&threshold=` — counts samples above threshold, converts to run-hours (÷ samples-per-hour for the cadence in force at the time: 240 at 15s, 360 at 10s — see `CADENCE_ERAS`), and splits hours into tariff buckets A/B/C/D (weekday/holiday × time-of-day, Asia/Bangkok via `tzOffsetMinutes: -420`) using `countValuesHour` + `isHoliday`, plus the finer TOU split `distHourFine` via `countValuesHourFine`

`WL` (wheel loader weights) deviates from the pattern: pivot queries, `/sum`, `/datacal`. `GET /plants/` is self-documenting — it returns usage examples plus every plant's tag list.

**`OFIL` and `Hour_OFIL` are two different databases** and are easy to confuse: `OFIL` (`REPL_OFIL_LOG`, added 2026-08-13) is the silo/rotary-screen drive output frequencies at 15s, served through the display layer; `Hour_OFIL` (`REPL_Hour_OFIL`) is cumulative hour counters at 60s with no gap fill and no cadence eras. **`Silo` is a third unrelated database** (`REPL_Silo_LOG`, added 2026-08-14): silo levels and weights gathered from several PLCs across the plant (Coating7, Coating1, RaymondMill2, PLC_Ofil) at 60s, values already logged in engineering units, so it goes through the display layer for **names only** (every divisor is 1) — `countSilo`'s `&threshold=` is in each tag's own units. Its `dbo.StringTable` is empty and, like OFIL's, deliberately not exposed.

When adding a new plant, copy an existing block, swap the database/table/column names (each DB uses differently-named tag tables — check the `/` route at the top of plants.js for the exact names), add it to the root `/` listing, and **give it a `CADENCE_ERAS` entry** — an unlisted machine silently falls back to 10s/360 (see the cadence gotcha). `Silo` (added 2026-08-14) is the most recent worked example — routes, era entry, root listing, a rename-only `TAG_DISPLAY` block, and `test/live/test-silo.js`. When fixing a bug in one plant's route, check whether the same copy-paste bug exists in all the other blocks (this has happened before, e.g. `TagIndex <> 'E'` instead of `Status <> 'E'` in the BM2_con avg route).

### Alarm-event module (`api/alarms/`, mounted at `/api/alm`, added 2026-07-10)

Self-contained module (per `alarm_event_api_spec.md`, repo root) exposing the FactoryTalk Alarms & Events historian `[Alarm_Event].[dbo].[AllEvent]`. Full endpoint manual with example responses: `api/alarms/README.md`. **The spec's DB address (172.30.1.225) is wrong — Alarm_Event lives on the same SQL Server as the historian (192.168.100.100)**; the module derives its pool config from `dbConfig_PROD` with `database:'Alarm_Event'` and a smaller pool (max 5). `ALARM_DB_USER`/`ALARM_DB_PASS` env vars override the credentials for a future db_datareader-only login.

- `index.js` — Router: self-doc `GET /` plus `/recent`, `/daily`, `/noisy`, `/dbhealth`, `/faults`, `/source/:sourceName`. Strictly read-only SELECTs, tagged-template parameterized.
- `pool.js` — named ConnectionPool with lazy connect/auto-retry: the API starts and serves `/plants` even with `Alarm_Event` unreachable; alarm routes return 503 `{"error":"Alarm_Event database unavailable"}` until it reconnects (no restart needed). `alarmRoute()` wraps every handler.
- `params.js` — pure `intParam`/`boolParam` validators (no mssql import; unit-tested offline by `test/alarm-params-unit.js`). Rule: missing/empty → default, non-integer or out-of-range → 400, **never clamp**.
- Error format is JSON `{error}` for 400/500/503 — a deliberate difference from plants.js's plain-text 500 (spec constraint).
- **FactoryTalk stores `EventTimeStamp` in true UTC** (verified 2026-07-10: `MAX(EventTimeStamp)` tracks `GETUTCDATE()` within seconds) — the opposite of the `REPL_*` DBs. Every alarm query therefore filters against `GETUTCDATE()` (never `GETDATE()`, which silently hides the newest 7 h of events) and shifts output `+7 h` (`PLANT_TZ_OFFSET_HOURS` in `index.js`) so the wire format matches the rest of the API (plant wall-clock, fake `Z`). `/daily` buckets are plant-local calendar days. Do not "fix" either direction.
- `dbo.AllEvent` has **no index on `EventTimeStamp`** — filtering on it scans the whole table (measured 2026-07-19: 1.3–2.2 s at 3.3M rows, growing with table size). Since 2026-07-19 every time filter instead seeks the **clustered `TicksTimeStamp` index**: `TicksTimeStamp` is the same true-UTC instant as a Windows FILETIME (100 ns ticks since 1601-01-01), and `EventTimeStamp` is exactly that value truncated to ms, so ms-aligned bounds translate exactly (`ticks.js`: lower `toFileTicks(from)`, upper `toFileTicks(to)+9999`, `ORDER BY TicksTimeStamp DESC`). Ticks params cross into SQL as strings (values exceed `Number.MAX_SAFE_INTEGER` → BigInt math); sentinel bounds `0`/`MAX_TICKS` replace `IS NULL OR` guards, which would force the optimizer back to a scan. Verified result-identical and 10–100× faster against production 2026-07-19 — don't revert to `EventTimeStamp`-only filters, and still never create indexes from the API.

### Data-quality context

Kepware periodically reconnects, leaving 10–30s logging gaps in the historian that can look like machine downtime. `2026-07-07-fillgap-kepware-gaps.md` (repo root) documents the bounded, bracket-checked gap-fill algorithm — read it before doing anything with gap/downtime/uptime calculations.

Implemented 2026-07-07: `fillGaps`/`applyFillGaps` live in `utils.js`, wired into 13 of the standard `/{plant}/:tagIndex/:tbf/:taf` window routes as an opt-in `?fillGaps=true&cadence=10&cap=90&tolerance=0.2` query param. Without the param the raw array passes through byte-identical; with it the response becomes `{fillGapsOptions, totalReadings, filledReadings, flaggedGaps, readings}` (chronological, synthetic rows marked `Filled:true`). On the `count{plant}` routes gap fill is **on by default** (changed 2026-07-09): gaps are bridged *before* counting, so run-hours aren't undercounted by logging blips, and a `fillGaps` audit block (`realReadings`/`filledReadings`/`flaggedGaps`) is appended to the response. Pass `?fillGaps=false` (the `fillGap` spelling also works) for the legacy raw count, byte-identical to the pre-2026-07-09 production behavior. The gate lives in `fillGapsForCount` in `utils.js`. Deliberately NOT wired to **WL** (event data — filling would fabricate weighing cycles), **Hour_OFIL** (cumulative counters — holding a counter flat understates it), or **countLC_CSH** (on-change logging, no cadence to fill against); these ignore the param everywhere. (LC_CSH's *window* route still honors opt-in `?fillGaps=true` if a caller insists, but the values are not meaningful.) Callers must pass `cadence` matching the tag's real logging rate. **LC_CSH logs on-change with no fixed cadence** (measured intervals 1–56s) — neither `fillGaps` nor sample-count run-hours are meaningful for it; a time-weighted calculation would be needed instead.

## Gotchas

- Queries use `mssql` tagged-template literals (`` pool.request().query`...${param}...` ``), which parameterize inputs — keep that form; don't switch to string concatenation.
- **Performance rework 2026-07-20** (verified byte-identical by `test/live/test-plants-perf-diff.js`, 56 checks vs old production): `/avg` and CT7_con's `/calCap` aggregate in SQL (`MIN/MAX/AVG/SUM/COUNT`) instead of fetching every row — 30-day window ~1.65s → ~70ms. The `avg`/`cap` values can differ from pre-2026-07-20 output in the last decimals (float summation order); `max`/`min` are identical. Window and `count*` routes still fetch rows (gap fill + tariff bucketing need per-row timestamps) but only `SELECT DateAndTime, Val` plus a separate 1-row TagName lookup — the old per-row `TagName` nvarchar join dominated transfer cost (~4× on the fetch). The window routes re-add `TagIndex`/`TagName` in JS in the same key order, so the wire format is unchanged; unknown tag / empty window behaviors are preserved exactly (empty `[]` / nulls, matching the old INNER JOIN + null-guarded JS helpers). The root `/plants/` listing runs its 17 tag queries via `Promise.all` (was sequential). WL routes untouched. Every `REPL_*` Float table has a covering `IX_Float*_TagIndex_Date (TagIndex, DateAndTime) INCLUDE (Val, Status)` index **except `REPL_LC_CSH`, `REPL_OFIL_LOG` and `REPL_Silo_LOG`** (all three only index `DateAndTime`; create it manually in SSMS when convenient — never from the API). Wide windows are still O(rows) on window/count routes — that's why `requestTimeout` stays 60s.
- **Logging cadence changes are handled per machine by `CADENCE_ERAS` (plants.js).** Run-hours are sample counts ÷ samples-per-hour, so a machine whose Kepware interval changed needs a different divisor either side of the change — and the historian keeps both cadences forever, so no single divisor is ever right for a window spanning one. `CADENCE_ERAS` maps each plant to its interval history; `erasFor()` splits a requested window at those boundaries, each era is counted with its own cadence (SQL-side via `runCountEras`, or in JS via `countErasJs` for the routes still on the JS pipeline), and `mergeEras()` sums count/hour and the distHour/distHourFine buckets. **Callers need no query parameters** — windows before, after, or spanning a change are all correct.
  - Recorded changes: the **whole plant moved 10s ⇒ 15s on 2026-08-06**, each machine at its own instant between 11:27:15 and 11:31:28 (measured per DB; every tag inside a database flips together). **RMM1 moved a month earlier, 2026-07-09 09:18:12**, when it was switched over on its own as a test.
  - A boundary is the timestamp of the *last row logged at the old cadence* (era n includes it, era n+1 starts just after). Each one shows the same signature in the raw rows: steady old cadence, a short Kepware reconnect burst of a few seconds, then steady new cadence.
  - **A machine that has only ever logged at one interval still needs an entry** — a single boundary-less era, e.g. `table.OFIL = [{ pointsPerHour: 240, cadence: '15' }]`. The fallback for an absent machine is 10s/360, which would report two thirds of a 15s machine's real run-hours — and only a sixth of a 60s machine's. `erasFor()` clamps such an era to the whole window (one query, the same flat single-era response body).
  - **To record a future change: append an era to `CADENCE_ERAS` (closing the previous one with the same timestamp) and change nothing else.** Never delete or edit a past era — history logged at 10s stays 10s forever, and dropping one silently corrupts every historical query. A rollback to 10s is a *third* era, not an undo.
  - `&pointsPerHour=` / `&cadence=` still force one cadence over the whole window (the pre-era-split workaround; also how Hour_OFIL's 60s cadence is passed).
  - Not in the table, and deliberately so: **Hour_OFIL** (60s, unchanged by the 2026-08-06 switch — verified), **LC_CSH** (on-change logging, no fixed cadence, so count-based `hour` is meaningless with any parameter), **WL** (event data).
  - In the table with a single 15s era: **OFIL**, whose database only started logging on 2026-08-11 (after the plant-wide switch), so it has no 10s history to split.
  - In the table with a single **60s** era: **Silo** (`REPL_Silo_LOG`, logging since 2026-08-14 15:54:31), `pointsPerHour: 60`. Measured over every interval in the table, not one sample. Unlike Hour_OFIL — the other 60s database — callers need no `&pointsPerHour=60`; being in the table is what makes `countSilo` correct by default.
  - Window routes don't era-split — raw rows are cadence-independent. Their opt-in `?fillGaps=true` defaults `cadence` to the era containing `taf` (`defaultCadenceFor`), so historical windows still fill at 10s and current ones at 15s; explicit `&cadence=` wins.
  - `fillGaps.fillGapsOptions` stays the flat `{cadenceS, capS, tolerance}` whenever the window sits inside one era, and becomes `{eras:[…], capS, tolerance}` only when it actually crosses a boundary. (RMM1 previously used the nested shape even for single-era windows; it now matches every other plant, and emits the audit block on empty windows like they do.)
  - Boundary constants use the file-wide fake-`Z` convention, and `toPlantDate()` parses naive `tbf`/`taf` as UTC too so both land on the same plant-wall-clock scale — parsing the naive form as server-local would put the two sides 7 h apart and assign rows to the wrong era.
  - Regression test: `test/live/test-cadence-eras.js` (starts the app in-process, diffs history against production on :3334). OFIL's and Silo's single-era entries are covered by `test/live/test-ofil.js` and `test/live/test-silo.js` instead — neither has a changeover for the era test's before/straddle windows to bracket.
- **RRM, OFIL and Silo are served through a display layer (`api/tagDisplay.js`) — their wire format is deliberately not the raw historian content.** The `REPL_RingRollerMill` tag table holds raw OPC names (`SiemensOPC.RingRollerMill.M208_Current`) and PLC integers scaled by 10 (feeder current by 100). Every RRM route renames the tag (`M208_Feeder_Current`) and divides the value, so consumers get real units; `/plants/RRM`, `/RRM/all`, latest, window (including the synthetic gap-fill rows), `/avg` and the root listing all go through it, and the DB is untouched.
  - **OFIL** (`REPL_OFIL_LOG`, added 2026-08-13) works the same way: the tag table holds raw Logix paths (`::[PLC_Ofil]OFIL_SILO4:I.OutputFreq`) and the drives log OutputFreq in hundredths of a Hz, so all five tags are renamed (`SILO4_OutputFreq`, `Rotary_Screen2..5_OutputFreq`) and divided by 100 (`2900 → 29`). Its `dbo.StringTable` is empty and deliberately not exposed — no plant route in this repo handles string tags.
  - **`countRRM`'s and `countOFIL`'s `&threshold=` is in the converted units** — it is multiplied back up by the tag's divisor before the SQL comparison, so `&threshold=1.4` on the RRM feeder means 1.4 A and `&threshold=5` on OFIL means 5.00 Hz. `count`/`hour`/`distHour`/`distHourFine` are sample counts and need no conversion.
  - Values are divided, never rounded (`137 → 1.37`). `null` passes through, and a TagIndex absent from the map keeps its DB name with divisor 1 — so an unknown tag or empty window behaves exactly as before (verified byte-identical). Tag 9 (`V204_Damper_Out_QW`) is renamed but **not** scaled: it is the raw Siemens analog output word, not a measurement — the damper's engineering value is tag 10 (`V204_Damper%`).
  - Adding a plant to `TAG_DISPLAY` **changes that plant's wire format**; treat it as a downstream-visible change. `test/live/test-full-endpoint-diff.js` doesn't wave these diffs through — it puts production's body through the same transform and requires an exact match, so the names and divisors are genuinely tested. It hardcodes `'RRM'` in ~8 places (`isRrmPath`) and would need generalizing before OFIL could be added to its plant list.
  - **`Silo` (added 2026-08-14) is the first RENAME-ONLY entry: every divisor is 1.** Its values are already real floats in engineering units, so nothing is scaled — but the raw historian names *misidentify the silo*, which is why it is in the table at all: `RaymondMill\Weight_Silo3` is silo **41**, `RaymondMill\Weight_Silo4` is silo **42**, `Coating7_Con\Net_Weight` is silo **1**, `LOADCELLSILO3NETWEIGHT` is silo **3**, and `[PLC_Ofil]TONSILOCSH[0..3]` are silos **1..4** (offset by one). Names supplied by the plant; all 28 are asserted verbatim by `test/live/test-silo.js`, which also checks no raw fragment (`SiemensOPC`, `PLC_Ofil`, `Coating7_Con`, …) reaches the wire. `countSilo`'s `&threshold=` is therefore in each tag's own units. The `scaleValue`/`divisorFor` calls are kept in the routes even though they are no-ops at divisor 1, so adding a divisor later needs no route changes.
  - **Silo's units are mixed across tags and deliberately NOT harmonised**: `SILO1_WEIGHT`/`SILO3_WEIGHT`/`SILO43_WEIGHT`/`SILO44_WEIGHT` read in the tens of thousands (kg), every other `*_WEIGHT` reads in tonnes. Don't infer a divisor from the shared `_WEIGHT` suffix — converting them is a separate decision that changes the wire format again.
- Timestamps: the DB stores naive Bangkok-local datetimes; the mssql driver (default `useUTC`) parses them as UTC, so JSON responses show local wall-clock time with a fake `Z` suffix. **This is intentional wire format — downstream apps depend on it; do not "fix" it by setting `useUTC:false`.** Internally, tariff bucketing reads the Date's UTC fields (`clock:'utc'` + `isHolidayUTC` in `utils.js`), which yields plant-local time on any server OS timezone.
- `count{plant}` routes return 400 if `threshold` is missing or non-numeric (previously they silently returned count 0).
- `count{plant}` responses are gap-filled by default, so their `count`/`hour`/`distHour` values intentionally sit higher than the pre-2026-07-09 numbers wherever logging gaps exist; `&fillGaps=false` reproduces the old behavior exactly. The window routes are unaffected — there `fillGaps` remains opt-in.
